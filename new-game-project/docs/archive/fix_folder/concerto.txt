Core Coding StandardsPhilosophy: This codebase requires strict adherence to type safety and data-driven design. We prioritize preventive maintenance over reactive bug fixing.1.1 Type Safety (Mandatory)All code must use strict static typing. This provides a 10-30% performance improvement and prevents runtime errors.The Standard:✅ Correct:GDScriptvar unit_manager: UnitManager = null
var deployed_units: Array[Unit] = []

func calculate_damage(attacker: Node, defender: Node) -> int:
    return 0

Architecture & Systems2.1 File Organization & StructureMaintain the following directory structure:Plaintextscripts/
├── Core/          # Core systems (Turn system, Grid)
├── Managers/      # Singleton-like managers (PhaseManager)
├── Resources/     # Resource definitions (CharacterData)
├── Units/         # Unit logic (Solo/Duo)
├── UI/            # UI Controllers
└── scenes/        # (.tscn files)
Scene vs. Script Decision:Use Scenes (.tscn): UI panels, Units, Visual Effects.Use Scripts (.gd): Managers, Resources, Autoloads, Pure Logic.2.2 Data-Driven Design (Resources)Do not use Dictionaries for game data. Use typed Resource classes.Current Resources: CharacterData, CharacterClass, Weapon, SupportConversation, MapData.2.3 Communication PatternsDependency Injection: Never use get_node() paths for systems. Inject dependencies via setup() or set_dependencies() methods.Signals: Use signals for cross-system communication. Never access nodes directly across hierarchy branches.Key Signals: unit_health_changed, phase_changed, bond_updated.2.4 Optimization: Dirty FlagsDo not update visuals every frame in _process. Use "Dirty Flags" to update only when data changes.GDScriptvar _state_dirty: bool = false
var state: TileState:
    set(value):
        if state != value:
            state = value
            _state_dirty = true # Flag change

func _process(_delta: float) -> void:
    if _state_dirty:
        _update_visual_state() # Update once
        _state_dirty = false

Workflows: Refactoring & Maintenance3.1 Safety & Verification WorkflowBefore committing any code or finishing a refactor, execute this checklist:Automated Scan: Run godot --headless --check-only --path "." to verify the entire project compiles.Script Validation: Check individual scripts if needed: godot --headless --check-only --script "path/to/script.gd".Linter Check: Ensure no warnings exist in the debugger.Save/Load Verify: Ensure any new data persists correctly.3.2 Common Pitfalls & ChecksA. Error Handling (100% Coverage)Every function must validate inputs.Check for null references immediately.Check array.is_empty() before iterating.Check has_method() before calling dynamic functions.Validate load() and instantiate() results.C. Array BoundsAlways validate indices before accessing arrays (e.g., Dialogue lines, Grid positions).3.3 Git WorkflowIgnored Files: .godot/, *.translation, export_presets.cfg.Commit Messages: Use semantic prefixes (feat:, fix:, refactor:, docs:).4. Refactoring GuideUse this guide when optimizing or cleaning existing code.4.1 Refactoring PrioritiesCritical (High): Security issues, performance bottlenecks, major duplication, missing type hints.Architectural (Medium): Breaking up oversized files (>500 lines), improving modularization.Cleanup (Low): Code style, minor optimizations.4.2 Handling Oversized FilesIf a file exceeds 500 lines or mixes concerns (e.g., UI and Logic):Identify Sections: Group related functions.Extract: Move logic to a new Manager or Helper script.Delegate: The original file should call the new script's methods.4.3 Code Analysis ChecklistWhen reviewing code, look for:High Complexity: Nested loops or excessive recursion.Duplication: Identical logic in multiple files (extract to shared module).Coupling: Tight dependencies between unrelated modules.Unused Assets: Dead variables, imports, or functions.5.
